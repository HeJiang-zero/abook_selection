# 一键刷新全部数据快照设计

## 背景

当前页面的主分析、每日 P&L 和 Book 分析会根据请求中的筛选期与验证期重新查询 ClickHouse。风险、平均盈利和马丁路由使用本地 JSON 快照；这些快照不会随着源表补数或修数自动重建。

当用户把验证期结束日改为 2026-07-16 时，主查询可以覆盖 7 月 16 日，但用户还需要一个明确、可审计的方式刷新本地快照，避免继续使用旧快照进行筛选和路由。

## 目标

1. 在左侧参数栏提供“刷新全部数据”操作。
2. 使用当前页面的筛选开始、筛选结束和平台参数刷新风险、平均盈利、马丁三个快照。
3. 三个快照成功生成后，自动重新执行当前分析，使最新快照和最新验证期数据在同一次页面结果中生效。
4. 刷新过程显示进行中状态，避免重复点击，并将每个快照的结果或错误返回给用户。
5. 刷新失败时不让不完整快照替换现有正式快照。

## 非目标

- 不改变筛选规则、Abook/Bbook 路由规则或 P&L 口径。
- 不在每次普通分析请求中自动重建快照。
- 不把验证期数据写入仅用于筛选期判定的风险、平均盈利和马丁快照；它们继续以当前筛选窗口为计算范围。
- 不尝试补齐 ClickHouse 尚未落库的数据；页面仍需通过覆盖信息提示源数据实际范围。

## 方案

新增后端刷新接口，由服务端复用现有三个快照构建器直接访问 ClickHouse。前端将当前日期和平台序列化为请求体，后端构建三份内存 payload，全部成功后再落盘。

接口：

```text
POST /api/abook/refresh-snapshots
```

请求体：

```json
{
  "selection": {"start": "2026-05-01", "end": "2026-06-30"},
  "platforms": ["mt5", "hh_mt5"]
}
```

响应包含总体状态和三个快照的状态、记录数、路径、筛选日期；异常时包含可展示的错误信息。刷新接口只接受允许的平台和有效的日期范围，并复用服务端已有的 ClickHouse 配置与 test/demo 过滤条件。

## 数据落盘与失败处理

每个快照构建器拆分为“生成 payload”和“写入文件”两个步骤。刷新接口先为三个目标文件分别写入同目录临时文件，写入完成后再进行正式文件替换。

替换阶段保留当前正式文件的内存/临时备份；若任一替换失败，尽力恢复已经替换的文件，并返回失败状态。这样普通的查询失败或 JSON 写入失败不会留下半份新快照。正式文件仍使用各模块已有的环境变量路径：`ABOOK_RISK_SNAPSHOT_PATH`、`ABOOK_AVG_PROFIT_SNAPSHOT_PATH` 和 `ABOOK_MARTINGALE_SNAPSHOT_PATH`。

## 前端交互

- 在左侧日期、规则和平台参数区域增加“刷新全部数据”按钮。
- 按钮使用当前筛选期和当前平台，不使用验证期日期；验证期由随后自动触发的分析请求使用。
- 刷新中按钮禁用并显示“正在刷新…”。
- 成功后自动调用现有分析接口，刷新主结果；清除旧的 Book 分析结果，避免继续展示旧日期的 Book 图表。
- 失败时保留旧分析结果，显示总体失败信息和具体快照错误，不声称数据已经更新。
- 普通修改日期后仍由用户点击“应用筛选与验证”执行主分析；只有点击“刷新全部数据”才触发快照重建。

## 代码边界

- `app/main.py`：新增刷新接口和错误映射。
- 新增一个小型快照刷新协调模块，负责调用三个构建器、校验 payload 和原子落盘；不把 ClickHouse 查询逻辑复制到接口中。
- `scripts/build_*.py`：保留命令行入口，并暴露可复用的 payload 构建函数；命令行模式继续支持单独刷新。
- `frontend/src/api.ts`：增加刷新接口调用。
- `frontend/src/App.vue`、`frontend/src/components/FilterSidebar.vue`：增加按钮、加载状态、成功/失败消息和刷新后自动分析。
- `static/`：通过现有前端构建流程同步生成生产静态资源。

## 测试设计

后端测试：

- 日期和平台参数正确传递给三个构建器。
- 三个构建器全部成功时，三个目标文件均被替换，响应返回成功及各自记录数。
- 任一构建器失败时，接口返回失败，正式快照内容保持不变。
- 无 ClickHouse 配置或非法请求时返回明确的 HTTP 错误。

前端契约测试：

- 左侧存在“刷新全部数据”按钮。
- 刷新接口使用当前筛选期和平台。
- 成功刷新后会重新调用分析，并清空旧 Book 分析状态。

回归验证：

- 运行完整 Python 测试套件。
- 构建前端并确认静态资源生成成功。
- 使用验证结束日为 `2026-07-16` 的请求检查主分析、每日 P&L 和 Book 查询的结束边界仍为 7 月 16 日（内部使用 7 月 17 日排他上界）。

## 验收标准

1. 用户在左侧点击“刷新全部数据”后，能看到三个快照分别成功或失败的结果。
2. 三个快照成功后，页面自动用当前筛选期快照和当前验证期重新计算。
3. 验证期设置为 2026-07-16 时，主数据查询包含 7 月 16 日落库数据。
4. 刷新失败不会破坏已有快照，也不会让页面显示为已使用最新快照。
5. 现有所有测试保持通过。
